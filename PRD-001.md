# PRD-001: Armador de Base de Conocimiento (MVP) — herramienta mínima para que un restaurador cargue su criterio de identificación de procesos fotográficos y mida si alcanza

## 1. Contexto y Problema

El museo tiene un acervo fotográfico numeroso por inventariar. Para cada obra hay que determinar el
**proceso fotográfico** con que fue hecha, porque de eso dependen su datación, su valoración y
—sobre todo— cómo se la conserva y se la manipula.

El restaurador hace ese trabajo con su experiencia y con el *Graphics Atlas* del Image Permanence
Institute (IPI/RIT), que usa como referencia autorizada. El Atlas describe 43 procesos y publica
los datos de 219 especímenes caracterizados en once facetas (tipo de objeto, formato, época,
asunto, soporte, color/tono, deterioro, brillo, textura, estructura de imagen y estructura de
capas).

El problema no es que falte información, sino que **no está en forma de decisión**. Los datos del
Atlas dicen qué valores se observaron en cada espécimen, pero no distinguen lo típico de lo
posible y **nunca dicen qué excluye a un proceso**. Además están desbalanceados: un proceso tiene
31 especímenes y otro tiene 1. Saber en qué fijarse, qué característica es decisiva y cuál solo
compatible, y qué descarta un proceso es conocimiento tácito del restaurador, y ninguna aplicación
lo adivina.

Este producto existe para que el restaurador vuelque ese criterio en una base de conocimiento, y
para responder lo antes posible una pregunta: **¿alcanza el esquema, cargado por él, para
reproducir sus propios dictámenes?** Cargar conocimiento sin evidencia de que el esquema alcanza
para decidir es el modo clásico en que fracasan los sistemas basados en conocimiento. Por eso la
herramienta incluye su propio instrumento de medición: un conjunto de control de obras ya
dictaminadas contra el que la base se puede ejecutar en cualquier momento de la carga.

Solo se construye la base de conocimiento. Ninguna aplicación la consume todavía.

### 1.1 Usuario

**Quién.** Un restaurador del museo. Experto en su dominio; no programador. No tiene permisos de
administrador en su máquina ni acceso a infraestructura del museo.

**Qué necesita.** Cargar conocimiento en ratos sueltos entre otras tareas, poder cerrar la
aplicación en cualquier momento sin perder nada, y retomar sabiendo dónde había quedado. Partir
de lo que ya trae el Atlas en lugar de una pantalla en blanco, y ver si lo que cargó reproduce
sus dictámenes, y por qué no cuando no lo hace.

---

## 2. Objetivos

- **Validar el esquema**: saber, con el conjunto de control, si las afirmaciones típico / posible /
  excluyente sobre las once facetas reproducen los dictámenes del restaurador (AC-04).
- **Que la base sea suya**: sus criterios de discriminación, no un volcado del Atlas.
- **Que sea trazable**: cada afirmación con su fuente.
- **Que el restaurador pueda iterar**: corregir la base a partir de lo que muestre cada ejecución
  del conjunto de control.

---

## 3. Requerimientos Funcionales

### 3.1 Ingesta

- **RF-01** — El sistema debe descubrir el catálogo de procesos desde `/identification/`, obteniendo
  nombre y `process_id` de cada uno, sin lista embebida en el código.
- **RF-02** — El sistema debe, para cada proceso, resolver vía `/change_process_idpage/` el nombre
  de su grupo y sus especímenes con id y nombre.
- **RF-03** — El sistema debe descargar la matriz completa de vectores de característica desde
  `/json_process_keyword_list/`.
- **RF-04** — El sistema debe registrar cada ingesta como una **instantánea identificada**: fecha,
  URL y hash de cada recurso descargado. Todo dato importado debe poder remitirse a la instantánea
  de la que salió.

### 3.2 Normalización

- **RF-05** — El sistema debe parsear los vectores de característica de forma robusta frente a la
  suciedad comprobada en la matriz: comas dentro de los valores, comas URL-encodeadas, diferencias
  de capitalización, espacios sobrantes y typos. El parseo no debe perder ni inventar valores.
- **RF-06** — El sistema debe detectar las variantes de un mismo valor dentro de la matriz JSON
  (p. ej. `Brwon`, `black` / `Black`, `Applied Color` / `Applied color`) y presentárselas al
  restaurador para que elija el término canónico, quedando las demás registradas como alias.

### 3.3 Curaduría

- **RF-07** — El sistema debe definir las facetas en dos niveles: **observaciones** (color/tono,
  deterioro, brillo, estructura de imagen, estructura de capas), que se miran en la obra, y
  **contexto** (tipo de objeto, formato, época, asunto, soporte, textura de superficie), que
  acotan el universo antes de recurrir al instrumental.
- **RF-08** — El sistema debe proponer, para cada proceso, un **borrador** del rango de cada
  faceta, agregando los vectores de sus especímenes, e indicar cuántos especímenes lo sustentan.
- **RF-09** — El sistema debe permitir clasificar cada par proceso-valor como **típico** (lo que se
  espera del proceso), **posible** (ocurre, pero no es característico), **excluyente** (es
  incompatible con el proceso y lo descarta) o **sin datos** (no determinado), partiendo del
  borrador y sin obligar a recorrerlo entero de una vez.
- **RF-10** — El sistema debe exigir fuente en toda afirmación: URL del Atlas con su instantánea, o
  "criterio del restaurador" con justificación opcional. No se puede guardar una afirmación sin
  fuente.
- **RF-11** — El sistema debe mostrar por proceso su cobertura — cantidad de especímenes,
  afirmaciones cargadas, facetas sin datos — como señal explícita de confianza.
- **RF-12** — El sistema debe permitir marcar qué procesos están presentes en el acervo del museo,
  para poder priorizar la carga.

### 3.4 Validación

- **RF-13** — El sistema debe permitir cargar un **conjunto de control**: obras que el restaurador
  ya dictaminó, cada una con sus observaciones por faceta y el proceso que él determinó.
- **RF-14** — El sistema debe ejecutar el conjunto de control contra la base y reportar, obra por
  obra, si la base llega al mismo proceso, a un conjunto de candidatos que lo contiene, o a un
  resultado incompatible.
- **RF-15** — El sistema debe explicar cada resultado: qué observación descartó qué procesos y qué
  afirmación lo sustenta. Un resultado sin explicación no sirve para corregir la base.

### 3.5 Atribución

- **RF-16** — El sistema debe mostrar en la aplicación la atribución y el aviso de copyright de
  IPI/RIT, y la URL de la fuente.

---

## 4. Requerimientos No Funcionales

- **RNF-01** — Ejecutable portable: se abre con doble clic, sin instalación y sin permisos de
  administrador. Desde el doble clic hasta poder trabajar: **< 5 s**.
- **RNF-02** — Sin servidor ni motor de base de datos externo. Nada que el área de sistemas tenga
  que aprovisionar.
- **RNF-03** — Operación completa sin red una vez hecha la ingesta.
- **RNF-04** — Todos los datos en almacenamiento local, respaldables copiando una carpeta y
  restaurables copiándola de vuelta.
- **RNF-05** — Trabajo incremental y durable: un cierre abrupto pierde **0 afirmaciones
  guardadas**; solo puede perderse la edición en curso, y al reabrir se puede retomar donde se
  dejó.
- **RNF-06** — Sin telemetría ni envío de datos a terceros. El único tráfico de salida es la
  descarga del catálogo y de la matriz durante la ingesta.
- **RNF-07** — Interfaz en español. Los valores del vocabulario conservan además su término en
  inglés tal como lo usa el Atlas.
- **RNF-08** — Buscar un proceso, abrir su ficha y guardar una afirmación responden en
  **< 500 ms p95**. La ingesta debe informar progreso y poder reanudarse.

---

## 5. Criterios de Aceptación

- **AC-01 (RF-01–RF-04)** — Dado un armador sin ninguna instantánea cargada y con acceso a la red
  (D-02), cuando el restaurador inicia la ingesta, entonces la completa por sí solo, sin
  asistencia técnica, y queda registrada una instantánea identificada con fecha, URL y hash de
  cada recurso descargado.
- **AC-02 (RF-10)** — Dado una afirmación sin fuente, cuando el restaurador intenta guardarla,
  entonces el sistema no la guarda; en consecuencia, la base tiene **0 afirmaciones sin fuente**.
- **AC-03 (RF-05, RF-06)** — Dado la matriz JSON con la suciedad descrita en RF-05 y sus variantes
  ya resueltas por el restaurador, cuando abre el borrador de cualquier proceso, entonces cada
  valor aparece una sola vez, con su término canónico, y quedan **0 variantes sin mapear**.
- **AC-04 (RF-13–RF-15)** (criterio duro) — Dado un conjunto de control cargado y el umbral que el
  restaurador acordó al empezar (D-04), cuando se ejecuta el conjunto de control contra la base,
  entonces hay **0 resultados incompatibles** y la base llega al mismo proceso que el
  restaurador, **y por las mismas razones** según la explicación de RF-15, en al menos el
  porcentaje de obras que él acordó.
  *El desacuerdo no es un fallo del test: señala que falta conocimiento o que el esquema no
  alcanza. Es la pregunta que este MVP existe para responder.*
- **AC-05 (RNF-05)** — Dado afirmaciones guardadas durante la curaduría, cuando se corta la
  energía, entonces al reabrir se conservan todas (**0 afirmaciones guardadas perdidas**) y se
  puede retomar donde se dejó.
- **AC-06 (RF-07)** — Dado una instantánea ingestada, cuando el restaurador abre la ficha de un
  proceso, entonces las facetas aparecen separadas en observaciones (color/tono, deterioro,
  brillo, estructura de imagen, estructura de capas) y contexto (tipo de objeto, formato, época,
  asunto, soporte, textura de superficie).
- **AC-07 (RF-08)** — Dado un proceso con especímenes en la matriz, cuando se abre su ficha,
  entonces cada faceta muestra como borrador la unión de los valores de sus especímenes y la
  cantidad de especímenes que lo sustentan (p. ej. 31 en Silver Gelatin, 1 en Bromoil).
- **AC-08 (RF-09)** — Dado un borrador, cuando el restaurador clasifica solo parte de los pares y
  cierra la aplicación, entonces al reabrir los pares clasificados conservan su estado y los
  demás figuran como sin datos.
- **AC-09 (RF-11)** — Dado un proceso con afirmaciones cargadas en parte, cuando se muestra su
  cobertura, entonces la cantidad de especímenes, de afirmaciones cargadas y de facetas sin
  datos coinciden con lo que hay en la base.
- **AC-10 (RF-12)** — Dado procesos marcados como presentes en el acervo, cuando el restaurador
  lista los procesos, entonces puede ver primero, o solo, los del acervo.
- **AC-11 (RF-16)** — Dado la aplicación abierta, cuando el restaurador busca la atribución,
  entonces el aviso de copyright de IPI/RIT y la URL de la fuente son accesibles desde la
  pantalla principal.

## 6. Fuera de Alcance

- **Identificar obras.** La herramienta no recibe fotografías del acervo ni emite dictámenes sobre
  ellas. La única excepción es el conjunto de control, donde las obras entran como instrumento de
  medición de la base, no como trabajo de inventario.
- **Una aplicación que consuma la base**, y con ella la publicación y el versionado de un paquete
  exportable. El respaldo lo cubre RNF-04.
- **Integración con el inventario del museo.**
- **Análisis automático de imágenes.** Ningún modelo de visión propone candidatos a partir de una
  foto.
- **Trabajo colaborativo**: un solo restaurador, una sola máquina. Sin varios autores, revisión por
  pares, edición concurrente ni control de acceso.
- **Que la herramienta modifique el Atlas o interactúe con IPI.** La relación con la fuente es de
  lectura, en un sentido, y por instantáneas.
- **Contenido del Atlas más allá del catálogo y la matriz**: la prosa de las fichas de proceso
  (fechas de uso, nombres alternativos, características clave, `What to look for`), las guías
  visuales en PDF y sus láminas de referencia, y las imágenes de ejemplo.
- **Fuentes distintas del Atlas** (bibliografía, colecciones de referencia de otros museos), y la
  conciliación entre varias fuentes.
- **Reingesta comparativa** contra una instantánea anterior.
- **Condiciones de observación** (magnificación, iluminación) por característica.
- **Conjunto de confusión** declarado. Los pares que la base no separa aparecen de forma empírica
  en los resultados del conjunto de control (RF-14, RF-15).
- **Orden de observación recomendado.**
- **Validación estructural** automática de la base.
- **Historial de cambios** por afirmación.

## 7. Riesgos y Dependencias

- **R-01** — Riesgo: **La fuente desaparece o cambia.** El Atlas responde solo por HTTP y su
  sucesión es incierta. → mitigación: instantánea versionada en vez de dependencia en vivo;
  operación sin red (`RNF-03`).
- **R-02** — Riesgo: **Datos sucios.** El parseo ingenuo pierde o inventa valores
  silenciosamente. → mitigación: parseo robusto especificado contra los casos reales (`RF-05`);
  el restaurador arbitra las variantes (`RF-06`).
- **R-03** — Riesgo: **Cobertura desigual.** Procesos con un solo espécimen producen rangos
  artificialmente estrechos que parecen conocimiento. → mitigación: cobertura visible por proceso
  (`RF-11`); distinción explícita entre excluyente y sin datos (`RF-09`).
- **R-04** — Riesgo: **El esfuerzo de carga se abandona** antes de que el conjunto de control sea
  significativo. → mitigación: priorizar por acervo (`RF-12`); borradores precargados para no
  arrancar de una pantalla en blanco (`RF-08`).
- **R-05** — Riesgo: **El esquema no alcanza.** Las once facetas podrían no bastar para
  discriminar casos reales. → mitigación: `AC-04` lo detecta mientras cambiar el esquema todavía
  es barato.
- **R-06** — Riesgo: **La base termina reflejando el Atlas y no al restaurador.** → mitigación: lo
  excluyente no se puede importar: solo él lo puede cargar (`RF-09`, `RF-10`).

### Dependencias

- **D-01** — Dependencia: el sitio del Graphics Atlas (`graphicsatlas.org`, por HTTP) disponible
  durante la ingesta, con `/identification/`, `/change_process_idpage/` y
  `/json_process_keyword_list/`.
- **D-02** — Dependencia: conexión a red durante la ingesta y solo durante la ingesta (`RNF-03`,
  `RNF-06`).
- **D-03** — Dependencia: la metodología de IPI *Photographic Process Identification Methodology
  and Controlled Vocabulary*, con la que el vocabulario canónico debe alinearse.
- **D-04** — Dependencia: un conjunto de control de obras ya dictaminadas por el restaurador, con
  sus observaciones por faceta, y el porcentaje de acierto que él acuerde al empezar (`RF-13`,
  `AC-04`).
- **D-05** — Dependencia: la confirmación del restaurador de la clasificación en tres niveles
  (típico / posible / excluyente) en lugar de una binaria (compatible / incompatible).
- **D-06** — Dependencia: tiempo del restaurador para cargar afirmaciones y correr el conjunto de
  control.

## 8. Stack Tecnológico

Cada decisión responde a un requerimiento; si el requerimiento cambia, la decisión se revisa.

| Componente | Decisión | Por qué |
|---|---|---|
| Plataforma | Windows 11 | Es la máquina del restaurador. |
| Aplicación | **Tauri 2**, distribuida como ejecutable portable, sin instalador | Ejecutable liviano que arranca en menos de un segundo, sin instalación ni permisos de administrador (`RNF-01`). Usa el WebView2 que Windows 11 ya trae. |
| Interfaz | TypeScript sobre WebView2, con React | Fichas de proceso, tablas de clasificación y reportes del conjunto de control (`RF-08`–`RF-15`). |
| Núcleo | Rust: cliente HTTP (`reqwest`), parseo de HTML (`scraper`) y JSON (`serde`), hash (`sha2`) | Ingesta reanudable (`RF-01`–`RF-04`, `RNF-08`), parseo robusto (`RF-05`) y ejecución del conjunto de control (`RF-14`, `RF-15`). |
| Persistencia | **SQLite** (`rusqlite`), en modo WAL, una transacción por cada afirmación guardada | Sin servidor ni motor externo (`RNF-02`); un cierre abrupto no pierde nada guardado (`RNF-05`); consultas locales por debajo de 500 ms (`RNF-08`). |
| Datos | Una carpeta junto al ejecutable con la base SQLite y los recursos crudos de cada instantánea, guardados con su hash | Se respalda y se restaura copiando la carpeta (`RNF-04`); cada dato remite a su instantánea (`RF-04`). |
| Red | Solo en la ingesta. Sin actualizador automático ni telemetría | `RNF-03`, `RNF-06`. |
| Pruebas | Pruebas unitarias en Rust con recursos reales de una instantánea como fixtures | El parseo no pierde ni inventa valores (`RF-05`, `AC-03`); el conjunto de control da resultados y explicaciones correctos (`AC-04`). |
